# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Prototype19 is a Unity **6000.3.10f1** (URP) online 2-player first-person shooter. Players fight a round. The winner then picks one of 5 cards, which modify their stats or grant abilities, and the next round starts on a random map. Networking uses **Netcode for GameObjects 2.4.4** over Steam P2P (Steamworks.NET). When Steam is not available it falls back to direct IP over `UnityTransport`.

## Building / running / verifying

- No build scripts, CI or test suites exist. There are no `.asmdef` files, so all game code compiles into `Assembly-CSharp`. The `*.csproj`/`.sln` files at the root are generated by Unity, so don't edit them.
- **After every code change, run `python3 tools/compile-check.py`.** It compiles `Assembly-CSharp` and `Assembly-CSharp-Editor` with `dotnet build` in about 2 seconds, whether or not the editor is open, and prints errors as `file:line:col`. It globs `Assets/**/*.cs`, so new files are picked up without regenerating the csproj files. It needs the generated root `*.csproj` files and `Library/ScriptAssemblies`, so open the project in Unity once on a fresh clone. It doesn't run Netcode's IL post-processing (RPC codegen), so check RPC changes in the editor too.
- Full check in the editor: when the editor is open, run `AssetDatabase.Refresh()` through `Unity_RunCommand`, then read `Unity_GetConsoleLogs`. When it isn't, run batchmode: `/Applications/Unity/Hub/Editor/6000.3.10f1/Unity.app/Contents/MacOS/Unity -batchmode -quit -projectPath . -logFile -`. Batchmode fails if the project is already open in an editor.
- Scenes in build order: `MainMenu` (0), `Level1`–`Level5` (1–5). Play `MainMenu` to test the lobby flow.
- Local multiplayer testing: Multiplayer Play Mode (`com.unity.multiplayer.playmode`) with **Tools → Steam → Use Steam In Editor** turned off. Virtual players never use Steam.
- Search the console for the log tags `[Steam]` and `[MapPool]`.

## Code layout

- `Assets/Scripts/Player/` holds **the core gameplay class** `FirstPersonController`, a `NetworkBehaviour` on the player prefab (the prefab is still at `Assets/Imports/ModularFirstPersonController/FirstPersonController/FirstPersonController.prefab`). It is a `partial class` split by topic. Go straight to the right file:
  - `FirstPersonController.cs`: all fields/inspector settings, the nested `WeaponSettings`/`PlayerSettings` structs, the static per-player dictionaries and `ResetSavedSettingsForPlayMode`, and the lifecycle methods (`Awake`, `Start`, `OnNetworkSpawn`/`Despawn`, `Update`, `FixedUpdate`, `LateUpdate`). New fields go here. This file must keep its name and `.meta`, because the prefab references its GUID.
  - `.Shooting.cs`: `TryShoot`, `FireBulletBurst`, `SpawnBullet`, `ShootServerRpc`, Flintknock recoil, crosshair/aim direction, reload, muzzle position, `FindSpawnedPlayer`, `ShouldUseNetworkSpawning`.
  - `.Settings.cs`: weapon/player settings get/apply/save/normalize and owner sync (`SyncWeaponSettings`, `SyncPlayerSettings`).
  - `.Health.cs`: `TryApplyDamage`, health bar UI.
  - `.RoundFlow.cs`: defeat (`HandlePlayerDefeatServer`), round wins, scoreboard, post-match UI RPC, card draws, spectator/winner camera, `ResetLevelAfterCardPick`, map-pool scene loading, and resetting players for the next round.
  - `.CardsUI.cs`: the card-pick UI (UI Toolkit): populate, keyboard selection, selection/pick RPCs, flip/pick animations.
  - `.CardEffects.cs`: `ApplyPickedCard`, ability RPCs (Flintknock/Payload/Beacon), `ApplyCardStatModifier(s)`.
  - `.Block.cs`: block/shield. `.Movement.cs`: ground check, jump, crouch, head bob. `.Animation.cs`: animator parameter helpers, `UpdateAnimator`.
  - `.Body.cs`: ragdoll, local-view setup, body renderers/materials (`IsSecondPlayerController`, `ApplySecondPlayerBodyMaterial`), shadow mode.
  - `.ArmSync.cs`: InnerGoober (first-person, parented to the camera) is the reference and is never modified. The owner publishes its inner hand poses in the `innerHandPose` NetworkVariable (root-relative, unscaled). In `LateUpdate`, every machine bends the OuterGoober arms (pitched by `LookLayer`) onto them with two-bone IK, so the outer muzzle sits on the shooter's `shootPoint`.
  - `.Editor.cs`: the custom inspector (`FirstPersonControllerEditor`, `#if UNITY_EDITOR`).
- `Assets/Scripts/Player/Bullet.cs` is the networked projectile. Most gameplay changes go into `FirstPersonController.*.cs` and `Bullet.cs`.
- `Assets/Scripts/Networking/` contains the lobby (`LobbyManager`, `LobbyUI`, `LobbyPlayerDisabler`, `LobbyCharacterPreview`), `SpawnPoint`, and owner-authoritative `OwnerNetworkTransform`/`OwnerNetworkAnimator`.
- `Assets/Scripts/Networking/Steam/` contains `SteamManager` (auto-bootstrapped, `DontDestroyOnLoad`), `SteamLobby` and `SteamNetworkingSocketsTransport`. **`docs/steamworks.md` documents the Steam integration in detail** (startup, hosting/joining, connection approval, disabling Steam, testing, shipping checklist). Read it before touching networking.
- `Assets/Scripts/PersistentNetworkManager.cs` keeps a single `NetworkManager` across scene loads and destroys duplicates that come from newly loaded scenes.
- `Assets/Scripts/Cards/Card.cs` is the `Card` ScriptableObject (stats + abilities). Card assets are in `Assets/Cards/`.

## Gameplay architecture (FirstPersonController)

- **Authority model:** the host is the server. Movement/transform is owner-authoritative (`OwnerNetworkTransform`). Damage, death, scoring and card draws run on the server (`TryApplyDamage` → `HandlePlayerDefeatServer`). Health and shield are `NetworkVariable`s. The code uses the legacy `[ServerRpc]`/`[ClientRpc]` attributes, often targeted at the owner through `ClientRpcParams`.
- **Shooting:** `TryShoot` → `FireBulletBurst` runs on the shooter's machine. A remote client (`ShouldUseNetworkSpawning()`: owner and not server) sends one `ShootServerRpc` per bullet with its live muzzle position and spawns a local **cosmetic** bullet right away. The server spawns the real networked bullet, and the two are matched by `shotId`. The host spawns real bullets directly. Recent bug fixes concern the spawn position of client projectiles, so keep the cosmetic and authoritative paths consistent.
- **Round loop:** death → server adds a round win, draws card indexes from `cardPool` → `UpdatePostMatchUiClientRpc` shows the cards UI (interactive only for the winner) → the winner picks → `ApplyPickedCard` → `ResetLevelAfterCardPick`. If `mapPoolSceneIndices` is set, it loads a random different scene with `NetworkSceneManager.LoadScene(Single)` and resets players in `OnLoadEventCompleted`. Player objects persist across the load, so `OnNetworkSpawn` does **not** run again. Don't send reset RPCs before or during a scene load. Doing that sent RPCs to objects being destroyed and caused `UnityTransport` UDP socket errors on clients, with only some players switching scenes.
- **Card effects:** `CardStat.target` (`CardStatTarget` enum) maps to fields in `ApplyCardStatModifier`. Abilities are matched by **string** `abilityName` in `ApplyPickedCard` (`"Flintknock"`, `"Payload"`, `"Beacon"`). A new stat target or ability needs code there and in the `Card.cs` enum. After a card is applied, stats are pushed to the owner with `SyncWeaponSettings`/`SyncPlayerSettings`.
- **Per-player state that survives scenes** (saved weapon/player settings, round wins, scoreboard) is kept in `static` dictionaries keyed by client ID and cleared in `ResetSavedSettingsForPlayMode` (`SubsystemRegistration`). Add new static state there too, because domain reload may be off.
- Player 2 is told apart visually by `IsSecondPlayerController`/`ApplySecondPlayerBodyMaterial` (red vs. blue).

## Conventions

- `LobbyManager.maxPlayers` (default 2) is also the Steam lobby's member limit. Much of the gameplay assumes exactly two players (red/blue, scoreboard).
- Changing the Steam App ID: update `SteamManager.AppId` and `steam_appid.txt`.
